# Hooks v1

Hooks run in the harness's synchronous agent pipeline. Configuration is loaded
when the agent is built; rebuild/restart to pick up manifest changes.

## Layout and resolution

Load global `~/.quasipilot/.hooks/hooks.toml`, then workspace
`.quasipilot/.hooks/hooks.toml`. Each root contains:

```text
.hooks/
├── hooks.toml
├── steering/checklist.md
└── code/audit.py
```

`file` resolves inside the declaring root's `<type>/` directory. Global hooks
run before local hooks, in manifest order. A local hook with the same `id`
replaces its global definition; `id = "...", enabled = false` disables it.

## TOML examples

```toml
[[hooks]]
id = "completion-checklist"
type = "steering"
trigger = "after.turn"
file = "checklist.md"
recursion = 1 # Default: maximum passes for this hook per logical turn

[[hooks]]
id = "reasoning-guidance"
type = "steering"
trigger = "before.tool"
file = "reasoning.md"
match = { tool = ["reasoning"] }

[[hooks]]
id = "commit-guidance"
type = "steering"
trigger = "before.command"
file = "commit.md"
match = { cmd = ["git"], args = ["commit"] }

[[hooks]]
id = "test-audit"
type = "code"
trigger = "after.command"
file = "audit.py"
match = { cmd = ["python", "python3"], args = ["-m", "pytest"] }
```

## Triggers and matching

- Triggers: `before.turn`, `after.turn`, `before.model`, `after.model`,
  `before.tool`, `after.tool`, `before.command`, `after.command`.
- Tool hooks cover every agent tool, including `reasoning` and `execute`.
  `match.tool` lists exact tool names.
- Command hooks observe `execute`: `cmd` lists accepted executable basenames;
  `args` is an exact, ordered argument prefix. Both must match when provided.
  Omitted `args` accepts any arguments; omitted `match` accepts all eligible events.
- Before/after use identical matching rules. Command matching uses the same
  parsed input for both phases.
- Only simple shell commands qualify in v1. Chains, pipelines, substitutions,
  subshells, control flow, and unsupported syntax skip command hooks with a
  diagnostic. Quoted operators are ordinary argument text. Tool hooks still run.
- `git commit -m "fix"` matches the example; `git -C repo commit` does not.
  No matching operators or executable-specific argument normalization in v1.

## Execution semantics

- A logical turn includes initial user input, user steering, and completion work.
  `before.turn` runs once. `after.turn` runs after a candidate final response,
  before closing the turn; steering resumes the agent within that turn.
  Each hook may run up to its `recursion` limit (positive integer, default `1`,
  valid only for `after.turn`). Hook-generated final responses can consume the
  remaining passes. Code hooks do not themselves request a model continuation.
- Steering files supply Markdown as tagged `harness_context` user messages,
  persisted and delivered to active message state. They are excluded from chat
  display, titles, and user-preference evidence. Before-model guidance reaches
  that model call; tool/command guidance reaches the next model call and cannot
  rewrite already-generated tool arguments.
- Code files are executable programs with shebangs. They run synchronously in
  hook order, with workspace cwd and JSON on stdin: schema version, trigger,
  session/turn IDs, runtime, and applicable input/result/error. Stdout/stderr are
  diagnostics, not steering. Hook subprocesses do not trigger agent tool hooks.
  They inherit the environment with the configured Python directory first on PATH.
  Timeout is 30 seconds; timeout/nonzero exit/launch failures produce a warning
  and dump-only `hook_result` metadata, then agent execution continues. Retained
  stdout/stderr are capped at 16,000 bytes each. Invalid manifests fail at load.
- Execute ordering: `before.tool → before.command → execute → after.command
  → after.tool`. After model/tool/command events include success/error/cancellation
  when their corresponding operation was entered.

`after.turn` runs on candidate completion only, not on errors or cancellation.
Steering re-entry retains the same turn and recursion counters. Parallel tool
invocations are serialized through their hook/execution sequences in v1.

## Code-hook input

Every JSON envelope includes `schema_version = 1`, `hook_id`, `trigger`,
`session_id`, `turn`, and `runtime` (cwd, Python interpreter, recorded Git state).
Turn/model events carry `input` messages or `result`; tool/command events carry
`tool` (name, args, call ID). Eligible command events also carry
`command = {raw, cmd, args}`. After events include `status` (`success`, `error`,
`cancelled`, or `interrupted`) and `result`, or `error_type` and `error`.
Results retain structured message content and artifacts, including exit codes.
